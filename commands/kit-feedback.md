# /kit-feedback — Knowledge Feedback Loop для 1c-cursor-kit

Перенос уроков из **технических инцидентов** в rules/skills kit. Канон алгоритма — `knowledge-feedback-loop.mdc`.

**Отличие от `/evolve`:** `/evolve` пишет в проектный `LLM-RULES.md` (поведение агента). `/kit-feedback` предлагает правки в **`1c-cursor-kit`** (технические pitfalls, чеклисты, validate checks).

## Approval gate (обязательно)

Команда и агент при обычной работе **никогда не редаруют kit без явного «да»** от пользователя на конкретное предложение.

Разрешено без одобрения: capture в проект, `note`, `show`, текст предложения с вопросом «переносим?».

Parse the argument: empty — полный проход по сигналам сессии; `note <text>` — записать один сигнал; `show` — только отчёт, без правок kit.

---

## Full pass (default)

### 1. Collect signals

Собрать в порядке приоритета:

1. **Текущая сессия** — инциденты, где ошибка ушла после 2+ итераций или причина была неочевидна.
2. **`docs/kit-feedback-signals.md`** в корне текущего проекта (если есть).
3. **Проектный `docs/changelog.md`** — записи с пометкой «pitfall» / «грабли» / недавние root-cause.
4. Текст, переданный с вызовом команды.

Пропускать эпизоды, уже перенесённые в kit (упомянуты в commit message kit или в `Evidence` существующего rule).

### 2. Capture и route

Для каждого сигнала заполнить: симптом → root cause → fix → повторимость.  
Маршрутизация — таблица доменов в `knowledge-feedback-loop.mdc` (шаг Route).

### 3. Gap analysis

По каждому candidate rule/skill: покрыто / частично / пробел.  
Если validate мог бы поймать заранее — отметить candidate check (например, check 14 в `cfe-validate`).

### 4. Propose (без записи в kit)

Нумерованный список предложений. На каждое:

- **Файл(ы) kit**
- **Что добавить** (фрагмент текста или описание diff)
- **Evidence** (сессия, changelog, дата)
- **Тип:** дополнение rule | дополнение skill | новый reference | validate check

Затем **один вопрос пользователю:**

> Переносим в 1c-cursor-kit? Укажите номера (например: 1, 3) или «нет» / «только changelog проекта».

**Без ответа с одобрением — шаг 5 не выполнять.**

### 5. Apply (только после одобрения)

- Править **только** одобренные пункты в `1c-cursor-kit`.
- Commit/push kit — **только по отдельной просьбе** пользователя.
- `install.ps1` — напомнить, не запускать без запроса.
- В одобренных сигналах в `docs/kit-feedback-signals.md` добавить строку `→ kit: <файл> (YYYY-MM-DD)`.

### 6. Post-run

Краткое резюме на русском: что предложено, что одобрено/отклонено, что осталось pending.

Если правило универсальное, но пользователь отказал от kit — оставить только в проектном changelog.

## note <text>

Записать один сигнал в `docs/kit-feedback-signals.md` текущего проекта (создать файл при отсутствии):

```markdown
## YYYY-MM-DD

- **Симптом:** ...
- **Root cause:** ...
- **Fix:** ...
- **Повторимость:** да|нет|возможно
- **Note:** <text>
```

Подтвердить одной строкой. **Не править kit.**

---

## show

Только чтение:

- pending сигналы из `docs/kit-feedback-signals.md`;
- подходят ли они под триггеры KFL;
- какие rules/skills кандидаты;
- были ли уже предложения в этой сессии.

Без записи в kit.

---

## Constraints (always)

- Не редактировать `1c-cursor-kit` без явного одобрения на конкретное предложение.
- Не коммитить kit без отдельной просьбы.
- Не подменять `/evolve` — поведенческие правила агента остаются в `LLM-RULES.md`.
- Не раздувать rules: один инцидент → одно точечное дополнение, не новый rule на каждый баг.
- Во время обычных задач — максимум одна рекомизация `/kit-feedback` в конце ответа (см. `knowledge-feedback-loop.mdc`).
